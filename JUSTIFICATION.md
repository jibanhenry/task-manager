# Justification — task-manager CLAUDE.md

**Commands.** I wrote exact commands (`pip install -r requirements.txt`, `pytest -v`, `flake8 .`) because the project had no lint tool at first, and I added `flake8` to `requirements.txt` so the lint line would actually run. The lint rule says to fix only warnings on changed lines, because the baseline already has 16 E302/F401 warnings and I did not want every task to turn into a reformat. Session 2 shaped this section most: Claude's first command used `python`, failed, and retried with `python3`, so I added the Python 3.9 / `python3` line, and Session 3 had no retry. If I had to cut it in half, I would keep the `pytest -v` and lint lines and drop the install line, since none of the three tasks needed new packages.

**Architecture.** I described routes → services → repositories honestly: there is no repository module, and the `TASKS`/`USERS` dicts are the data store, owned by their service file. Session 3 shaped it most: Claude refused to call `get_user` from `services/tasks.py` in Session 2 but did it in Session 3, so I added the cross-service rule to settle that question instead of leaving it to Claude each time. To cut in half, I would drop the `app.py` and `routes/api.py` lines, since no session touched them.

**Conventions.** Every rule points at `services/users.py`, because Session 1 showed Claude copies `get_user` almost line for line when told to. Session 2 shaped this section most, and it was my honest failure: "follow `services/users.py`" plus "raise `ValidationError` for bad input" led Claude to add an empty-title check during a style refactor, so I added the rule that refactors must not change behavior. The test rule came from Session 1, where Claude added a `NotFoundError` test on its own although the v1 rule only covered new functions. To cut in half, I would remove the `if task_id not in TASKS` line, because the `get_user` reference already shows that pattern.

**Do not touch.** Each rule names the code that would break: `handle_app_error` reads `AppError.message` and `status_code`, and the tests depend on task ids 1 and 2. This section did not change across sessions, which I take as evidence it worked: in Session 1 Claude added a new test instead of tightening the existing `pytest.raises(Exception)` assertion. To cut in half, I would keep the `AppError` and test-assertion rules and drop the `requirements.txt` rule.

**Team version.** First, I would move the `python3` / Python 3.9 line into a personal `CLAUDE.local.md`, because it describes my Mac, not the project, and teammates on other setups would get wrong instructions from a shared file. Second, several rules end in "ask first" (refactor behavior changes, editing tests, adding dependencies). With three developers, "ask" needs a destination, so I would change these to "flag it in the PR description" and require changes to CLAUDE.md itself to go through code review, so one person's session cannot quietly change the rules for everyone.
